# 给 AI 的 Mod 开发标准

这份只给正在帮作者写钢铁指挥官 Mod 的 AI。玩家说明在仓库 README。不要为了答一句去读管理器的 `MainViewModel.cs`。

核对日期：2026-10-08。数字以当天仓库为准，过期了就改数字，不要沿用记忆。

不要向作者追问用哪条路把 Mod 交出去。下面的规则与交件方式无关。

## 你是谁

你只生成客户端体验向的 Mod。你不改管理器，不在游戏运行时改写别人已经编译好的 DLL，也不承诺「装了这个就不会封号」。

Data Error 的公开后果是：这一局判负，并且不能重连。它不是已经核实的永久封禁。游戏自己的缺陷和丢包也会写出同一条记录。

## 现在的版本

- 管理器：`1.3.17`。
- 社区目录 `catalog.json` 的 `updatedAt`：`2026-10-08T09:15:00Z`。
- 目录里现有普通条目的 `minManagerVersion` 是 `1.3.14`。CUT 新手指南是素材包，字段是 `1.3.15`。简介里若写着「需要 1.3.13」，那是旧句子。管理器只认 `minManagerVersion` 字段，不认简介。
- 安装器附带的 MelonLoader 是 `0.7.3`。作者按这个加载器来写 MelonMod。

## 先看体积

写代码、导出文件、填目录之前，先量这个 Mod 要交给玩家的字节。算上主 DLL，以及要一起装的文字、视频和其他文件。文件还没有时，按作者说的素材估；导出之后用真实长度再量一次，再写目录。哈希和体积不要问作者，由 `python scripts/stamp_hashes.py` 填写。

管理器能下载的每一份文件都必须小于 100MB。100MB 是 `100 * 1024 * 1024` 字节，也就是 104857600。`size` 达到或超过这个数，下载会被拒绝。git 同样拒绝达到或超过 100MB 的单个文件。

按量到的结果只走一条：

- **一个 DLL，并且它小于 100MB。** 按后面的普通 Mod 写。用 `parts` 分片，`minManagerVersion` 写 `1.3.14`。不要加 `bundle`，也不要加主包和副包。
- **仍然只是一个 DLL，但这个 DLL 达到或超过 100MB。** 用 `parts` 把这一个 DLL 切成若干片，每片小于 100MB，按顺序拼回去等于整份 DLL。这仍是一个文件，不是主包加副包。不要用 `bundle`。`minManagerVersion` 写 `1.3.14`。
- **要带文字、视频或其他素材，合在一起达到或超过 100MB，或者本来就要装多个文件。** 不要做成一个达到 100MB 的单文件，也不要用 `parts` 去装多个文件。按下一节写成主包和副包，然后仍然遵守本文后面的身份、简介、挂钩和禁止事项。

## 超过限制：主包更新，副包不动

只在上一节走到第三条时使用。

一个 Mod 仍然只有一个 `id`。用 `bundle`，不用 `parts`。`bundle` 和 `parts` 不能同时有。

`bundle` 是数组，每个成员有四项：

- `path`：装进游戏后，相对这个 Mod 目录的位置。不能是绝对路径，不能含 `..`。同一条里不能重复。
- `file`：文件在社区目录仓库里的路径。
- `sha256` 和 `size`：这一份文件自己的，由脚本填写，不要手改。

其中一份是主包，文件名必须和条目 `file` 的文件名相同。条目顶上的 `sha256` 和 `size` 等于这一份主包，不是所有成员加起来。校验脚本会核对此事。现有的 CUT 新手指南就是这样：主包大约 854KB，文字包和各段视频包分开列。每个成员都要小于 100MB。

副包是常态素材：文字、视频，以及其他不随这次版本改动的文件。

`minManagerVersion` 不得低于 `1.3.15`。素材包按文件夹安装从这一版开始。不要为了跟上当天的管理器写成 `1.3.17`，除非这个 Mod 还依赖更晚才有的行为。`1.3.13` 和更早的管理器不读这个字段。玩家自行导入不受这个门槛限制。

更新只动主包时：

- 换主包的字节，并让脚本重写主包的 `sha256`、`size`，以及条目顶上的 `sha256`、`size`。
- `version` 写成这个 Mod 自己的新版本。
- 没改过的副包：`path`、`file`、`sha256`、`size` 保持和上一版逐字相同。不要重新导出一遍再当成新文件。
- 不要把视频或文字再打进主包。
- 不要改 `id`。改了 `id`，管理器会把它当成另一个 Mod，玩家等于第一次安装，全部文件都要下载。

删掉一个副包、或只改 `path` 不改字节，管理器不一定会把它显示成可更新。判断看的是哈希集合，不看路径。要让玩家看到更新，至少让一份仍在列表里的文件哈希发生变化，通常就是主包。

`1.3.17` 的 `DownloadBundleAsync` 会把 `bundle` 里的每一份都重新下载，再整份换进本地库。副包哈希没变也下载。

所以现在不能告诉作者或玩家：只更新主包、副包不会再下。作者按上面保持副包不变，是为了目录形状正确，不是因为管理器已经会跳过它们。

管理器已经会判断「要不要更新」：主包哈希变了，本地没有这份新哈希，条目就是可更新。它还不会在下载时跳过未变化的成员。

第一次安装、本地副包对不上目录哈希、或作者真的改了某个副包，那一份本来就要下载。这一点以后也不变。

这条路上不要做的事：

- 不要把 `bundle` 写成 `parts`。
- 不要让任何一个成员达到或超过 100MB。
- 不要让条目顶上的 `sha256` 等于所有文件拼起来的哈希。它必须等于主包。
- 不要承诺 `1.3.17` 的玩家更新时只下载主包。
- 不要改管理器来迁就这一个 Mod。

## 谁能下载

玩家手里的管理器能不能下载这个 Mod，靠的是目录字段 `minManagerVersion`，不是 Mod 里的代码，也不是简介里的句子。

标准里由管理器执行的版本门槛，只对一种行为生效：玩家通过这个管理器下载或更新 Mod。玩家从别处自行下载，再导入管理器（DLL、压缩包或文件夹），或者用别的方式放进游戏，都不受这个门槛限制，也没有因此产生的问题。`minManagerVersion` 不检查导入。旧版管理器把文件导入之后，可以照常启用。启用时的挂钩确认仍按下一节，跟文件从哪来无关。

`1.3.14` 和更高版本在通过管理器下载、更新前比较这个字段和自己的版本：

- 当前版本低于字段：拒绝下载，并提示先更新管理器。
- 当前版本等于或高于字段：允许下载。
- 字段空着：不设下限。
- 字段写错（带 `v`、有第四段、有前导零，例如 `v1.3.14`、`1.3.14.1`、`1.03.14`）：`1.3.14` 及更高版本当成认不出，同样拒绝下载。合法写法是恰好三段整数，每段 0 到 65535，例如 `1.3.14`。`1.3.9` 低于 `1.3.14`。
- 已经在本地、目录哈希没变：不会为了这个字段再下一遍。自行导入、放进游戏目录、启用、停用，都不经过这次核对。

`1.3.13` 和更早的管理器不读这个字段。写成 `1.3.17` 也拦不住它们，它们仍会下载，包括带 `parts` 的包。

新 Mod 怎么填：

- 门槛只写在这个字段里。不要写进 DLL，也不要写进简介。
- 「先看体积」判定为普通单 DLL：写 `1.3.14`。这是目录约定。`1.3.13` 也会拼分片，只是它不看这个字段。
- 「先看体积」判定为主包加副包：不得低于 `1.3.15`。
- 确实依赖更晚才有的管理器行为：写成第一个具备该行为的版本。要挡住 `1.3.14` 到 `1.3.16`，就写 `1.3.17`；`1.3.17` 及更高才能下。
- 说不清这个行为从哪一版开始有：停下来问作者。不要猜成当天的管理器版本。
- 校验脚本允许字段缺失。字段在时，必须是上面的三段写法，否则脚本拒绝。脚本通过，只说明格式合法，不说明数字选对了。

## 先问完再写

缺了下面任何一项，就停下来问作者。不得用占位符，也不得从文件名猜作者名、版本或支持哪一端。

哈希和体积不要问作者。那两项由 `python scripts/stamp_hashes.py` 填写。体积走哪一条，按「先看体积」自己量，不要改问作者。

- **身份。** 玩家看见的作者名，写入 `author`。联系方式不写进简介。
- **标识。** 提议一个 `id`：小写字母、数字、连字符，并与文件夹名相同。请作者确认目录里还没有这个 `id`。
- **名称。** 中文显示名，写入 `name`。
- **简介。** `summary` 只写三件事：玩家能做什么、用哪个键、正式服 / 测试服 / 两者。目录没有单独的游戏端字段，端写在简介里。不要写管理器版本号。不超过 400 字。
- **译文。** 按现有目录，再起草英文、德文、日文、俄文的 `locales` 名称和简介。给作者看过再定稿，不要自己当成已经确认。
- **版本。** 分开问两件。`version` 是这个 Mod 自己的版本。`minManagerVersion` 按「谁能下载」和体积结果填写。说不清依赖的是哪一版管理器行为时，停下来问，不要猜成当天的版本。
- **分类。** 让作者从下面选一个，不要凭名字里的「伤害」或「经济」替他选。
  - `OverlayUI`：叠在画面上的信息。
  - `QoL`：少点几下、更好操作，不改演算。
  - `Camera`：只动镜头。
  - `CombatAssist`：战斗过程中的辅助。选这个仍要按下一节看挂钩，分类本身不是风险等级。
  - `Economy`：补给、售价、收支的显示或操作。
  - `ReplayDebug`：回放或调试。
  - `Misc`：以上都不是。
- **标签。** 几个短词，写入 `tags`。标签不能代替分类。
- **冲突。** 和哪个已有 `id` 同时装进游戏会坏。没有就明确写没有。有的话双方都要列入 `conflicts`，`reason` 用字符串。对方 `id` 必须已经在目录里。不要自己和自己冲突。这一条由维护者写入 `catalog.json`，你先把双方 `id` 和原因问清楚。
- **预览图。** 有或没有。有则路径是 `preview`，写了 `previewSha256` 就必须和文件一致。
- **安装位置。** 默认 `type` 为 `MelonMod`。只有作者明确要插件、UserLibs 或 UserData 时，才改成 `MelonPlugin`、`MelonUserLibs`、`MelonUserData`。不要自造第五种。

## 两套「必填」不要混

校验脚本 `scripts/validate_catalog.py` 会拒绝的是：空的 `id`、`name`、`file`，以及非法的 `sha256`、`size`、分类、冲突、分片、素材包和 `minManagerVersion`。`minManagerVersion` 可以整段不写；写了就必须是三段整数。

`author`、`summary`、`category`、`version` 在脚本里可以缺。脚本通过，不等于简介合格。本标准仍要求你在上一节问齐，再交给作者看。

目录合同：

- `sha256` 和 `size` 用脚本写，不要手改。
- `parts` 和 `bundle` 不能同时有。每个分片小于 100MB，按顺序拼回去必须等于整文件的 `sha256` 和 `size`。
- 主包加副包时，顶上的 `sha256` 和 `size` 等于主包，成员规则见「超过限制」。
- 单文件超过 100MB、git 放不下时，才用 https 的 `originUrl`。哈希仍然必填。体积预检已经要求把这种文件切开或拆成主包和副包，不要先用 `originUrl` 绕过。

改完二进制后运行 `python scripts/validate_catalog.py`。不过，就不要告诉作者可以上架。

## 管理器会怎么看你的 DLL

启用前，管理器用静态扫描看 Harmony 挂钩，不看文件名，也不看注释。它不会改你的 DLL。没有 DLL 的目录项等级是「未检测」，不拦下载。

等级以返回类型和挂钩目标为准，不看函数体里有没有真的跳过原函数。

- **低。** 挂钩目标不在下面两张表里。启用时只显示，不弹确认。界面、相机、点游戏自己的按钮，属于这里。
- **中。** 挂在观察点或部署时间上，但又不是下面的「高」。启用前要玩家确认。
- **高。** 两种情况，启用前都要确认。一是前缀的返回类型为 `bool`，且目标在观察点或部署时间里。扫描器只看这个返回类型，即使函数体从不返回 false，也仍是高。二是后缀挂在部署时间那三个方法上，不论返回类型。
- **未检测。** DLL 读不出来，或手工补丁对不上目标。不要把它说成低风险。

观察点：

- `FightActor.ReduceLife`
- `DamagePerformer.Perform`
- `Player.AddSupply`、`Player.AddRoundSupply`、`Player.ReduceSupply`、`Player.SetSupply`
- `BattleStatisticManager.OnFightEnd`
- `BattleSystem.OnFightOver`

部署时间：

- `ProcessController.IsStateTimesUp`
- `ProcessController.GetMaxStateTime`
- `ProcessController.GetDeployTime`

作者侧约定：

- 次级界面、相机、好友列表不要挂到观察点。
- 如果必须在观察点上只读：前缀里的异常自己吃掉，让原函数继续执行；前缀不要声明为返回 `bool`；不改伤害、补给、部署时间的返回值。
- 正式对局只提交游戏本来就有的操作（撤回、道具、加速投票）。回放里才允许改部署计时，并且用「当前是不是回放」当门闩。门闩不成立时执行原函数。
- 游戏版本对不上、方法已经不存在时，整段挂钩不装。

不要用名字里的「伤害」「经济」给 Mod 定级。不要把挂钩目标藏进字符串去骗扫描。扫描看的是 Harmony 特性。

## 不要做的事

- 不要改管理器源码来迁就一个 Mod。
- 不要在游戏进行中改写已安装的 DLL。
- 不要把一次 Data Error 写成永久封号。
- 不要照抄简介里的「1.3.13」。
- 不要为了让扫描显示「低」而把会改演算的逻辑藏进运行时拼出来的调用。
- 不要追问或写明交件渠道。
- 不要在体积还没量之前就决定用 `parts` 还是 `bundle`。

## 核对

2026-10-08 对照过下载和校验。偏差已改在上文。大 Mod 的主包和副包写在本文「先看体积」和「超过限制」里。

- 扫描器 `LogicFrameRiskScanner.GradeHook`：观察点或部署时间上、返回类型为 `bool` 的前缀是高；部署时间上的后缀是高；其余挂在这两张表上的是中。上文按返回类型写，不按「函数体是否真的跳过」。
- 校验脚本：拒绝空 `id`、`name`、`file` 以及非法哈希、体积、分类、冲突、分片、素材包和 `minManagerVersion`。字段可以不写。`author`、`summary`、`category` 可以缺。上文把「脚本会拒」和「AI 仍要问」分开。分片和素材包成员的 `size` 必须小于 104857600。
- 下载门槛：`ManagerVersionFloor` 从 `1.3.14` 起，只在通过管理器下载和更新时比较 `minManagerVersion`。自行导入不检查。更早的管理器不读该字段。上文按这个界限写，不把抬高数字说成能挡住 `1.3.13`，也不把门槛说成能挡住导入。
- 素材包：`DownloadBundleAsync` 在更新和第一次安装时逐个下载全部成员，没有按本地哈希跳过。`BundleIsComplete` 看哈希集合：新哈希或变了的哈希会显示可更新；少了一个成员，或只改路径而哈希还在，不会单凭这一点显示可更新。`check_bundle` 要求成员在仓库里，每份小于 100MB，`path` 不能重复或越出目录，`bundle` 与 `parts` 互斥，顶上的 `sha256` 和 `size` 等于文件名与 `file` 相同的那一份主包。素材包按文件夹安装从 `1.3.15` 起。
- 目录现状：管理器 `1.3.17`，`catalog.json` 的 `updatedAt` 为 `2026-10-08T09:15:00Z`。普通条目的 `minManagerVersion` 为 `1.3.14`，CUT 新手指南为 `1.3.15`。简介中的「1.3.13」仍视为旧文案。
- 正文不规定交件渠道。
